## 2. draw() and Forth 2.0's GFX_LINE

### 2.1 Where the time goes

The figures in `LEAP_C_DRAW_SPEED.md` agree with the code. `draw()` is `LIB_DRAW` (`src/runtime/library.asm`): it
clamps the four arguments into the byte cells `GFX_LINE_X0..Y1`, then jumps to `GFX_LINE` in
`platform/kernel/graphics/graphics.asm`. That file is the vendored Leap V2 platform file, with Leap-C's recorded
deltas D6 to D24. Its `GFX_LINE` is the one Forth replaced. For each pixel it:

- reloads everything from memory cells;
- calls `GFX_WRITE_PIXEL`, which runs `GFX_PIXEL_ADDR_SETUP` (the full address from x and y, through
  `ROW_BASE_TABLE` and `BIT_MASK_TABLE`) and then `GFX_SET_ATTR` (through `GFX_CELL_ATTR_ADDR`'s bounds checks);
- does the error test with `MATH_NEGATE16` and two `MATH_COMPARE16` calls.

`plot()` runs `LIB_ARGS`, then `LIB_OVATTR`, then `GFX_PLOT_CLIPPED`, then the same `GFX_WRITE_PIXEL`. Most of its
1,700 T goes to the call and argument path, not the pixel.

### 2.2 What a port is

Forth's `GFX_LINE` (`kernel/graphics/graphics.asm` at `v2.0`, `GFX_PIXEL_AT` to `LINE_DELTA`) fits Leap-C closely:

- **Same pixels.** Its major-axis loop draws the points of the e2 form both projects inherited. Forth's report
  checked this on 48,561 lines; the IDE's bitmaps agree.
- **Same attributes.** It writes a cell's attribute (in high resolution, the 8x1 byte at the bitmap address +
  `$2000`) with the first pixel drawn in that cell. That is what Leap-C does now, pixel by pixel. Leap-C's delta D22
  already uses the + `$2000` rule.
- **The alternate registers are free.** Forth keeps r, dmin and dmaj in HL', DE' and BC'. Nothing in Leap-C uses
  `exx`: not the interrupt handler, not the float core, not the runtime, not the cartridge code. The library jump
  table's `LX_PLOT` contract does not change, and `plot()` would not use them.
- **OVER needs adding.** Forth dropped it; Leap-C's `over(1)` draws by exclusive-or. A flag bit and a branch in the
  pixel loop cost about 20 T a pixel and about 12 bytes, with `GFX_WRITE_PIXEL` included.
- **Clean-up.** `point()` (`GFX_READ_PIXEL`) would compute its address with `GFX_PIXEL_AT`. The `GFX_PIXEL_*` and
  old `GFX_LINE_*` scratch cells go.

The change would be a new platform delta (D25) on `graphics.asm` and the matching change to delta D1
(`sysvars.inc`), recorded in `platform/UPSTREAM.md` and its `MANIFEST`. `make check` verifies both. The code's
source would be named there as 2068-Forth v2.0, the same owner's project. `tools/provenance.py` compares against the
stock ROMs only, so it is not affected.

### 2.3 Off-screen ends: two options

**A. Keep Leap-C's rule (recommended).** `LIB_DRAW` keeps moving off-screen ends to the edge, as the manual's `draw`
entry says. `GFX_LINE` then only ever gets on-screen byte ends, so the port needs only Forth's on-screen part:

- Forth's off-screen walk goes (`.walk` to `.wy`, 54 bytes), with `LINE_BRES` (18 bytes; only the walk calls it).
- The 16-bit setup can be 8-bit.
- **The pixels are the same as now for every input, off-screen ends included.** The existing tests, the manual's
  `// pixel:` lines and the 115-program cartridge comparison should show no change at all, and any change would be a
  defect.

**B. Forth's rule.** `draw()` would draw the on-screen part of the true line between signed 16-bit ends. This would
fix what the manual's note warns about (`draw(-10, 50, 100, 60)` now starts at (0, 50) with another slope). But:

- the pixels change for every line with an end off the screen. The manual's note, `tests/lib/gfx/draw.c` and any
  program that relies on today's behaviour change with them, so it belongs in the changelog as a change of
  behaviour;
- `GFX_LINE_X0..Y1` become four 2-byte cells. They are platform cells (V2's `EXTENSION_ARG0..3` aliases):
  `check_ram_layout.py`, `memguard.py` and `poweron.py` follow. No library uses them; libraries reach the screen
  only through `LX_PLOT`;
- the walk to the screen costs about 270 T a step, as Forth measured. `draw(0, 0, 32767, 1)` would take about
  10M T (3 s), where it now draws at once. Forth's exact jump over the off-screen part (about 130 bytes) does not
  fit in Leap-C's HOME (section 2.4).

Option A gives all the speed with no change in behaviour. B is a language change: if wanted, decide it on its own
terms, and it can follow A later (A's loop is B's drawing half).

### 2.4 ROM bytes

HOME has **481 bytes free**, against a reserve floor of 384 (`build/budget.json`), so there are **97 bytes of room**.
The cartridge HOME is built from the same sources.

| | Bytes |
|---|---:|
| Removed: `GFX_PIXEL_ADDR_SETUP` 64, `GFX_WRITE_PIXEL` 51, `GFX_LINE` 206, `BIT_MASK_TABLE` 8, `MATH_COMPARE16` 26 (no other caller) | -355 |
| Forth's code, assembled alone (`GFX_PIXEL_AT` to `LINE_DELTA`) | 397 |
| Option A: Forth's code without the walk and `LINE_BRES` (-72), plus OVER (+12), 8-bit setup (about -10) | **about 320-340** |
| Option B: Forth's code plus OVER (+12); `LIB_DRAW`'s clamping (63 bytes with `LIB_CLAMPX/Y`) shrinks to a copy (about -38) | about 410 - 38 |

- **Option A: about 15-35 bytes freed.**
- **Option B: about 15-25 bytes added**, within the 97 bytes of room. Its exact jump (+130) would not fit.

These figures are from the symbol files and a scratch assembly of Forth's routine. The real figure would come from
`make budget` after the port.

### 2.5 Speed (estimates, to be measured)

| | Now | After (option A) |
|---|---:|---:|
| A pixel of `draw()` | about 1,700 T (the IDE's figure) | about 300 T (Forth's 280 + the OVER test) |
| 864 x `draw(10, 10, 100, 60)` | 2,005 frames | about 450-550 (Forth: 422; Leap-C adds the call, argument clamping and attribute) |
| Spinning squares | 1,644 frames | about 500-600 (Forth: 522) |
| A `plot()` call | about 1,700 T | about 1,450-1,500: the address and attribute path loses about 200 T; the call and argument path is unchanged |

`plot()` is not a reason to do this. It takes the faster pixel code for free, because `GFX_WRITE_PIXEL` is shared.
A loop of `plot()` calls stays slow next to `draw()`, as in Forth: its PLOT benchmark gained 2.7%.

### 2.6 What the port would involve, if approved

1. Delta D25: `GFX_PIXEL_AT`, `GFX_LINE` (on-screen part, byte ends, OVER), `LINE_XSTEP`/`YSTEP`, `LINE_ATTR`,
   `GFX_WRITE_PIXEL` and `GFX_READ_PIXEL` on the new address code. Remove the old routines, cells and
   `MATH_COMPARE16`. Update the budget ledger.
2. Tests that fail on 1.1.0, as Forth's did:
   - a Python model of the old e2 loop compared with the ROM's bitmap and attributes over many lines (both modes,
     OVER, off-screen ends clamped);
   - T-state ceilings for a row, a column and the diagonal.
3. `make test`, `make fuse`, `make test-cart` (the 115-program comparison), then `make repro` and `make qualify`.
4. A release (1.2.0): the ROM bytes change. That means a new identity CRC (not `$E90E`), a new cartridge build, new
   `.sym` addresses (the names are unchanged; none of the CHANGELOG's stable names is involved), and new ROMs for
   TSRun and the IDE.

Leap V2 BASIC's `LINE` has the same routine. That is the Leap project's decision; nothing here depends on it.

**Waiting for the owner:** option A, B, or neither, and the release that carries example 11.

## 3. Update, 2026-11-01: option A built

The owner chose **option A** and the port is built: branch `draw-speed` in this repository, report
`docs/milestones/M13-draw.md`, platform delta D25. `manual-example-11` (section 1) is pushed. Both go out together
in **1.2.0**, since the ROM bytes change. This supersedes the estimates in sections 2.4 and 2.5.

### 3.1 The same pixels

`tools/linetest.py` (`make lines`) holds a Python model of `draw()` as 1.1.0 defines it: ends clamped to the
edge, V2's e2 loop, an attribute per point, OR or XOR. It runs programs of `draw()` calls in ZEsarUX and compares
the bitmap, the attributes and, in mode 1, the second display file byte for byte.

| Check | Result |
|---|---|
| The model against the **1.1.0 ROM** (88 lines x mode 0/1 x over 0/1) | all equal |
| The model's sensitivity: the e2 loop with the other tie rule | differs on 56 of 352 lines |
| The new ROM, seed 2068: 48 fixed lines (corners, edges, single points, ends at ±32,768, lines wholly off the screen, 24 directions) + 400 random (half with ends in -300..560, -250..450), each x mode 0/1 x over 0/1 | all equal |
| The new ROM, seed 7: 248 lines, the same four ways | all equal |
| The new loop modelled in Python against the e2 form, 200,000 random lines | 0 differences |

### 3.2 Speed (ZEsarUX, T-states; one call less an empty program)

| | 1.1.0 | 1.2.0 | |
|---|---:|---:|---:|
| `draw(0, 100, 255, 100)`, 256 pixels | 369,298 | 60,702 | 6.1x |
| `draw(100, 0, 100, 191)`, 192 pixels | 283,902 | 51,563 | 5.5x |
| `draw(0, 0, 255, 191)`, 256 pixels | 388,184 | 81,691 | 4.8x |
| `draw(10, 10, 100, 60)`, 91 pixels | 136,701 | 29,461 | 4.6x |
| A `plot()` call (100 in a loop, the loop taken off) | 1,366 | 1,029 | -25% |

Forth 2.0's row, column and diagonal take 58,954, 52,286 and 83,901 T. The per-pixel figure is now about 240-320 T.
`plot()` gained more than section 2.5 estimated: its pixel now goes through the line loop as a line of one point.
What remains is mostly the call itself (`LIB_ARGS`, `LIB_OVATTR`, the bounds checks).

Your speed test should come out at roughly a quarter of 1.1.0's frames; for example, the 864 x `draw(10, 10, 100, 60)`
test should take about 430 frames instead of 2,005. That is scaled from the figures above, not measured in TSRun.

**Forth's PLOT against `plot()`.** The owner asked whether Forth's PLOT is faster. It is: about 500 T a call
(counted, not measured), against `plot()`'s 1,029 now (1,366 in 1.1.0). Forth's PLOT pops two cells and goes
straight to `GFX_WRITE_PIXEL`. A C library call also records its caller for error reports (`LIB_ARGS`), applies
`inverse` (`LIB_OVATTR`) and checks 16-bit bounds.

### 3.3 Sizes

HOME: **95 bytes freed** (481 -> 576 free; ledger L86), against the estimate of 15-35. The edge tests are not
needed because the ends are always on the screen, and `plot()` shares the line loop. The EXROM is unchanged. No RAM
layout change: the old cells stay defined, unused.

### 3.4 What changes for the IDE in 1.2.0

- **New ROM images**, so a new cartridge identity (not `$E90E`; the 1.2.0 release will publish it) and new `.sym`
  addresses. No stable name changes.
- `GFX_READ_PIXEL` now takes C = x, B = y, and `MATH_COMPARE16` is gone. Neither is a stable name.
- The library ABI (the jump table at `$3FD0`, `LX_PLOT`) is unchanged.
- `draw()`'s pixels and attributes are unchanged for every input, so the IDE's bitmap comparisons should not move.

### 3.5 Regression

All passed on the branch, with no failures: `make check`; `make test` (every exec suite including the manual's 271
examples, the lexer, the shell, e2e with the 1,166-program corpus through RUN, float, poweron, tape, canary); `make
fuse` (Fuse 1.9.1, corpus 1,016/1,016); `make test-cart` (the 115-program cartridge comparison with RUN: reports and
final screens identical); and `make lines`. Details: `docs/milestones/M13-draw.md` section 4. `draw-speed` is
pushed; 1.2.0 (with `make repro`, `make qualify` and the release) waits for the owner.
