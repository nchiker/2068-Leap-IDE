# Leap Arcade: the space plan (banked cartridge map and the items deferred for lack of room), 2026-11-10

Written as a handoff at the end of a long session (language batches 4 and 5, the v4 size pass). It does two things: (1) fixes the **banked cartridge map** that raises a game from 16 KB to **32 KB** (owner decision, 2026-11-10: "we are building on a limit that I don't believe is there"), and (2) orders **everything that was deferred or squeezed for lack of space**, with the dependency, the byte cost and the test for each. Start with `docs/HANDOFF.md` (state of the branches), then this file.

## 1. The limit, checked against the manual
Source: Timex Sinclair 2068 Technical Manual (`https://www.retromaniek.pl/wp-content/uploads/2019/09/Timex-Sinclair-2068-Technical-Manual-best.pdf`, 401 pages; text copy made with `pdftotext -layout`).
* **The cartridge connector supports "up to 64K of addressable memory. The full 64K is not normally utilized (e.g., due to need for access to RAM for the machine stack)"** (section 1.1, page 6). Memory is selected as eight 8 KB chunks; the Home Bank is the default and a chunk not selected in the Dock or Extension bank is the Home one.
* **Selection:** the HSR (port `$F4`): each set bit enables that chunk in the Dock bank when port `$FF` bit 7 = 0 (Extension ROM when 1; the two are mutually exclusive); all zero = the whole Home bank (section 2.1.13.5).
* **Display RAM** is Home chunk 2 (primary file) and chunk 3 (second file) and "is accessed independently by the video hardware. The software only needs to enable it when actually reading or writing it" (section 5.1.1, page 76). That is the documentary basis for banking over the display chunks (it is **not** a hardware test: `ARCADE_HARDWARE_NOTES.md` checklist item 0 stays open).
* An LROS "may contain code in Chunk 3"; the manual describes switching between a Dock chunk and the shadowing Home chunk to continue execution at the next instruction (page 76, points 1-4). So code or data in Dock chunks 2, 3, 6 is **not forbidden by the hardware**; it was a design choice (`ARCADE_CARTRIDGE_MAP.md`: "copy only").
* **Nothing in the manual covers a cartridge larger than 64 KB** (that would need bank-switching hardware on the cartridge itself and a DCK format beyond `parseDck`'s one 64 KB DOCK bank). Not planned.
* **What we ship today:** DOCK chunks 0, 1, 4, 5 = 32 KB of the possible 64 KB (`SHIPPED_CHUNKS = [0, 1, 4, 5]` in `arcade-link.js` and `build-runtime-*.mjs`; the `.dck` is 32,777 bytes). The runtime fills chunks 0-1 (v4: 14,612 of 16,384 after the size pass), the game chunks 4-5 (Leap Runner about 15,378 of 16,384, Vaults about 15,999). Chunks 2, 3, 6, 7 stay RAM while the game runs: the two display files, the working RAM at `$C000-$DFFF` (pools, tables, shadows) and the variables / stack at `$E000-$FFFF`.

## 2. The banked map (decision: 32 KB per game, layout ready for 40 KB)
| Window | Chunk | Content | Reached |
|---|---|---|---|
| `$0000-$3FFF` | DOCK 0, 1 | runtime (14.6 KB in v4) + the bank service | always mapped |
| `$8000-$BFFF` | DOCK 4, 5 | the **mapped game**: code, hot tables, tileset, string pool, sprite frames the draw reads every tick, sound effects (the ISR reads them), the asset directory | always mapped |
| `$4000-$7FFF` | DOCK 2, 3 | **bank A (chunk 2) and bank B (chunk 3): up to 16 KB of cold assets** (= the 32 KB total) | mapped for the length of one copy |
| `$C000-$DFFF` | DOCK 6 | **bank C** (+8 KB later, total 40 KB): data only | mapped for one copy; its RAM twin (the working RAM) is invisible meanwhile, so the destination is never in `$C000-$DFFF` and the copy runs from chunk 0 |
| `$E000-$FFFF` | RAM | variables, stack: **never** a Dock chunk (the stack lives here) | - |
RAM the game still has: display files `$4000-$5AFF` / `$6000-$7AFF`, working RAM `$C000-$DFFF`, variables and stack `$E000-$FFFF`.

**The bank primitive** (new in every runtime, about 100 bytes; room: v2 6.9 KB, v4 1.7 KB, v3 593 bytes (see item 2 of section 4: port the size pass first)):
* `RT_BANKCOPY`: `A` = bank (0 = chunk 2, 1 = chunk 3, 2 = chunk 6), `HL` = offset in the bank (0..8191), `DE` = destination (RAM, **not** in the bank's own window), `BC` = count. It builds the `$F4` value from the shadow (`V_SHADOW_F4`; today `$33` in play), ORs the chunk bit, `OUT`s, `LDIR`s, restores the shadow value, returns. A copy runs with interrupts **enabled**: the ISR "only touches RAM chunk 7 (variables), the AY and ports, never a chunk that is ever paged" (`isr.asm`, rule 1 of the map), the stack is in chunk 7, and the routine itself runs in chunk 0.
* **Rules for every caller** (put in the contract and the runtime test): no display-file access, no call into a routine that touches `$4000-$7FFF` / `$5B00-$5FFF` / `$7B00-$7FFF` (v3 / v4 keep RAM routines at `$5B00`), no `RT_SHOW` etc. between map and unmap; the copy is atomic with respect to the main thread. 21 T per byte: 256 bytes about 5.4k T, a whole 8 KB bank about 3 refreshes (scene start only).
* **Streaming reads** for data larger than the scratch: `RT_BANKREAD` copies the next N bytes of a bank stream into a small staging buffer (a decoder for the RLE worlds and maps calls it per 256 bytes).
* **Staging RAM:** a fixed region for one scene's copied data; its size and place are measured per runtime (v2 has `$CE00-$DFFF` free; v3 / v4 need a map of free RAM first: slice B0 below).

**The asset directory** (in the mapped game): a table of `{bank, offset, length}` for each banked asset (24 bits), written by the linker; compiled code and `LOADMAP` / world / effect loads go through it.

**What the compiler banks, automatically, in this order, while the mapped game would otherwise not fit:** the world map (`world_src`) and the floor plan (`map_src`) of a WINDOW / VIEW3D game (decoded from the bank at scene start), screen MAPs (`LOADMAP` then copies to staging and calls `RT_LOADMAPPTR`), whole tilesets of other scenes, sprite frame sets used only by one scene (copied into the frame pool when the scene is entered), and large sound effects (copied to a RAM sound buffer on `PLAY`, since the interrupt cannot read a bank). Scenes (batch 4) are the natural unit: `ENTER` loads what its scene needs. Never banked: code, the tileset the redraw reads every tick, hot sprite frames, the ISR's data. The Studio shows two budgets (mapped 16 KB, banked 16 KB) and the linker says which asset moved and why.

**Shipping:** the DCK / flat image writes chunks 2 and 3 (and 6) only when something is banked (`SHIPPED_CHUNKS` becomes per build); a game that fits stays a 32 KB `.dck`, byte-identical to today.

**Risk to settle first (slice B0):** (a) real hardware: the SCLD must keep displaying RAM while a Dock chunk is mapped over it (manual: yes; checklist item 0: untested); (b) TSRun, ZEsarUX 13.0 and Fuse 1.9.1 must agree on mapping a Dock chunk over RAM chunks 2 / 3 / 6 with the interrupt running (a test cartridge copies a known 8 KB pattern from each bank every frame while a game draws: the displayed picture and the copied bytes must match on all three).

## 4. Everything deferred for lack of room, in the order I would do it
1. **Faster three-channel sound tick** (in progress as a design; contract in `ARCADE_LANGUAGE_BATCH5.md` Part C items 17-18, revised 2026-11-10). The first version (PR #5) costs about 2,160 T per refresh and stores 12 bytes per refresh. The revision moves the work to the compiler: it computes each refresh's AY register values and stores only the changes (`n`, then `n` pairs `reg, value`; the first entry holds all 11 registers), the runtime tick just writes pairs and updates `AY_SHADOW`. Targets: no-change refresh <= 250 T, typical <= 600 T, worst <= 900 T, code <= 100 bytes (the 142-byte `SND_TICK3` in the `$0068-$00FF` gap goes away). Changes: `sound.asm` in v2 / v3 / v4, `convertSfx` (delta encoder), `m10-runtime-sound.mjs` model, `sound-model.js` (size accounting only; the editor edits records, unchanged), docs. The format never shipped (PR #5 is not merged), so it can be replaced freely; keep the byte 3 = 3 header.
2. **Port the v4 size pass to v3** (v3 is now the tightest runtime, 593 bytes free). The cold-code lane (`boot`, `video`, `assets`, `text`, `tileops`, `keys`, `sound`) is nearly the same source; apply the same method (`/z80-skills:shrink-z80`, one worker per lane, patches verified in disposable worktrees as this session did; it must be invoked by the owner). Target: >= 1 KB free in v3. Needed by items 3 and by B1 on v3.
3. **Blank-cell fast path of the scrolling window (v3)**: +1.1 KB, measured -28 % repaint on sky-heavy worlds like Leap Runner (`ARCADE_RUNTIME_API_V3.md`, "Blank-cell path: not included"); watch the +8 % worst case on solid worlds (re-measure; the platformer's budget is 130,000 T).
4. **Per-scene window / 3D view and world reload** (`ARCADE_LANGUAGE_BATCH4.md` section 9): `RT_WORLDRELOAD` (decode `world_src` again, v3), the ray array reload and a ray-mode off switch (v4), so a title scene shows no world and a level restart reloads it. With the banked map the source is decoded from a bank, so do it after B1 / B3 or keep it in the mapped game. Language: a scene-level `NOWINDOW` / `NOVIEW` or `WORLD name` clause (decide when writing the contract).
5. **Pre-scaled billboards (v4)**: measured billboard cost 15k T (16x16) to 72k T against the contract's 9k; Vaults is 0.49 % of ticks over budget. About 10x cheaper per pixel with pre-scaled sets (`ARCADE_RAYCASTER_CONTRACT.md` section 9); the sets are data: bank them (B3) and copy the sets of the enemies in view. Needs the v4 room (now 1.7 KB) plus staging RAM.
6. **MUSIC (M4b)**: three AY channels in the interrupt. Do after item 1 (the delta-stream tick is the player's core) so the interrupt cost is known; music data is read by the ISR, so it stays mapped or is copied to a sound buffer.
7. **Not space, but queued:** gap items 10 (`RANDOMISE` / `BORDER` / `FLASH` words partly done) and 11 (32-bit scores); Studio debugger; real-hardware tests.
8. **Rejected for now:** a game with both WINDOW and VIEW3D (needs the 4.5 KB scroll engine inside v4: 1.7 KB free), textured walls (speed, not space), cartridges above 64 KB.

## 5. Decisions (owner, 2026-11-10)
* **Revised sound design accepted** (delta stream computed by the compiler); build it **before PR #5 is merged**, so the 12-byte-group format never reaches `main`.
* **Chunk 6 as a third bank: later** (the directory is designed for it now).
* **Banked-asset control: automatic placement, with a per-asset `mapped` / `banked` / `auto` override in the project document only, not in the language** (the owner took the recommendation; the "project document only" reading is mine, as with the per-scene display override). A `BANK` clause in the language can be added later without breaking anything.
* **Still the owner's to type:** `/z80-skills:shrink-z80` runs. The v3 pass was started on 2026-11-10 (two workers, patches to be verified and combined by the main thread).
