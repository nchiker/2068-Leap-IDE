# Phase 1 spike, native Z80 side: results

Measured with `node run-native.mjs --all` (TSRun machine, stock TS2068 ROMs present but never run; program loaded at
`$8000`, `DI`, no frame interrupt; CPU stepped one instruction at a time until RAM[`$5B00`] = `$A5`).
T-states are exact (`m.tstates` delta, including the marker store). Frames = T-states / 58,688.
TSRun has no contention, so these are best-case figures; ZEsarUX-style 48K contention on `$4000-$7FFF`, if the real
machine has it, would make the B1/B2 numbers worse (they write to the screen all the time). Unverified on hardware.

| Program | Frames | T-states | Binary bytes | Run-time tables (RAM, not in binary) | Matches reference |
|---|---:|---:|---:|---|---|
| `b1_generic.asm` | 100.7 | 5,907,766 | 313 | 64 B (shape 32, sprites 32) | yes (bitmap SHA-256 equal) |
| `b1_special.asm` | 56.5 | 3,316,068 | 690 | 544 B (pre-shifted shapes 512, sprites 32) | yes |
| `b2_tiles.asm` | 57.2 | 3,359,027 | 608 | 3,328 B (routine table 256, map lists 3,072) | yes |
| `b2_tiles_data.asm` (extra) | 88.9 | 5,217,764 | 201 | 1,664 B (tile table 128, map 1,536) | yes |
| `b3_crunch.asm` | 29.1 | 1,705,336 | 882 | 4,000 B (sieve flags) | yes (550, 16673, 14032) |

"Binary bytes" is what sjasmplus writes: code plus initialised data (there is almost no initialised data; tables are
built at run time and that time is in the T-state totals). All five programs finish with no cap issue (cap 5,000
frames; the longest uses 101). All five assemble with no errors or warnings and use only documented opcodes (no IXH/IXL/SLL).

## What specialisation bought (B1)

Generic to specialised: 1.78x faster (100.7 to 56.5 frames, per blit 3,711 to 2,083 T including everything), for 2.2x the
code (313 to 690 B) plus 512 B of pre-shifted tables. Pre-shifting removes about 100 T/row of shifting; the rest of the
gap is the per-row address step: the generic blit pays about 27 T/row for `inc h / and 7 / jr nz` row stepping, the
special one pays 4 T/row (`inc h` only) because the unrolled blocks are split at character-cell boundaries.
The per-blit setup in the special version is still about 600 T (screen-address arithmetic, two self-patched `JP`s,
two cell fix-ups); a precomputed y-to-row-address table would save roughly another 5 to 8 percent. Not done.

## Techniques

* **B1 generic.** 24-bit window (D, E, C), `SRL D / RR E / RR C` x7 unrolled, entered through a self-modified `JR`
  displacement (6 x (7 - n)), so a shift by n costs 24 T x n with no loop counter. SP is the shape pointer (`POP DE`,
  safe because of `DI`; `CALL`/`RET` happen outside the blit). Row stepping is the standard `inc h` plus cell fix-up.
  Positions are stepped incrementally (x += dx, subtract 240 once; y += dy, subtract 176 once), which is exactly
  (x0 + dx t) mod 240 because dx <= 8 and y step <= 4. A left-shift variant for n >= 5 (max 3 shifts instead of 7) would
  save roughly 15 percent of the generic time; not done.
* **B1 special.** Eight pre-shifted copies (4 bytes per row: b0 b1 b2 pad) built at start by seven 24-bit shifts
  (roughly 15k T, counted). A row is `pop de / pop bc / 3 x (ld a,(hl) / xor r / ld (hl),a)` = 86 T with `inc l`/`dec l`
  between bytes. Rows alternate direction (boustrophedon) so there is no return to column 0. A row unit is 14 bytes and
  identical for all rows, so three copies of an 8-row block are enough: block A entered at unit k = y&7, block B whole,
  block C entered at unit 8-k; entry addresses are patched into two `JP`s. Odd k means the first unit runs right to left,
  so L starts at col+2. Trap: SP is the source pointer, so the blocks cannot be a `CALL`ed subroutine (the return
  address would be pushed onto the shape table); they are inline.
* **B2 `b2_tiles.asm`.** Tile pixel data is compiled into 16 routines of immediates (`ld (hl),n / inc h`) generated by
  the assembler from the SPEC formula (no tile table at run time). The map is built at run time from the SPEC formula,
  but stored as a list of routine addresses per row, and the **stack pointer is the instruction pointer**: every tile
  routine ends in `RET`, which pops the next tile. A sentinel (address of `rowend`) is patched over the word after the
  32 visible tiles of the row, parked in BC, and restored afterwards (BC/IX/D survive the tile routines). No map wrap is
  needed: c + t <= 62 < 64. Cost per tile 126 T = 80 (writes) + 28 (`inc h` x7) + `ld h,d` + `inc l` + `ret` (10); row
  overhead about 200 T; map build about 90k T. It is 15.75 T per byte written.
* **B2 `b2_tiles_data.asm` (extra, not asked).** Tile bytes read from a table, map is a table of 8 x tile numbers,
  tiles drawn alternately top-down and bottom-up so H never resets. 22 T per row. Shows the price of data-driven
  tiles against code-compiled tiles: 1.55x slower, 3x smaller binary.
* **B2 ideas judged not better.** Pre-rendering the 64-column strips (12 KB) and copying 32 bytes per pixel row with
  `LDI` is 16 T/byte, the same as the threaded routines (15.75), and the scroll-by-one-byte trick (`LDIR` the screen
  left, draw one new column) would not redraw from the map as SPEC says. `PUSH`-based writes need the SP for the
  destination, which conflicts with return threading, and a word-table lookup per tile pair costs more than the bytes
  it saves.
* **B3.** Flags array placed so that it ends at `$10000` (`$F060-$FFFF`): the sieve's inner loop is
  `ld (hl),a / add hl,de / jr nc` = 30 T, and "j >= 4000" is simply the carry. Only primes below 64 are sieved, marking
  from i*i (same flags as the full algorithm). Flags are cleared with 2,000 `PUSH HL` from SP = 0 (23k T), and counted
  with `add a,(hl)` in chunks of 200 (sum fits a byte). The LCG runs 71 T per step with HL = x, BC = copy, DE = 3,
  IY = running sum, 80 steps unrolled: `ld b,h / ld c,l / xor h / add iy,bc / add hl,hl x2 / add hl,bc / add hl,de`.
  The mod 32768 mask is not applied per step: the low 15 bits of 5x+3 depend only on the low 15 bits of x, and the
  garbage bit 15 only matters for the sum, whose correction is 32768 x (parity of bit 15 over all steps) mod 65536, which
  is accumulated for 4 T per step by `xor h` (bit 7 of A) and applied once at the end. About 1.42M of the 1.71M T is the
  LCG loop.

## Traps and notes

* Return threading and the SP-as-source trick both require `DI`; any NMI or interrupt would corrupt the stack-borne
  data. A real game with a frame interrupt would have to patch these (for example copy the thread to the stack top
  per row, or accept the interrupt only between rows).
* The harness counts the instruction that stores the marker (about 13 T) and nothing after it; the assembly runs
  from `$8000` with no initial delay. No benchmark writes `$A5` to `$5B00` before the end (verified by the matches).
* The B1 hot loops read and write the bitmap only; attributes are not touched. All five bitmaps/results equal
  `reference.mjs` exactly (bitmap SHA-256, and B3 values 550 primes, x = 16673, s = 14032).
* Files: `run-native.mjs` (harness; writes assembler output to a temp dir, nothing else outside this directory),
  `b1_generic.asm`, `b1_special.asm`, `b2_tiles.asm`, `b2_tiles_data.asm`, `b3_crunch.asm`.
