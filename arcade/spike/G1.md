# Gate G1: native Z80 or bytecode? (Phase 1 result, 2026-11-09)

**Decision: native Z80.** Measured on TSRun (58,688 T per frame, no contention). Details: `native/RESULTS.md`,
`leap/RESULTS.md`, `xip/RESULTS.md`. Reproduce with `node native/run-native.mjs --all`, `node leap/run-leap.mjs <file>`,
`node xip/e1.mjs` (and `e2`, `e3`). All outputs were checked bit-exact against `reference.mjs`.

## Speed (frames for the same job; lower is better)

| Benchmark | Native Z80 (hand) | Leap-C 1.2.0 (native, compiled on the machine) | Leap V2 BASIC 2.1.2 (bytecode VM) |
|---|---:|---:|---:|
| B1: 1,592 XOR blits of a 16x16 shape | 100.7 generic / **56.5 specialised** | 9,349 | 24,535 |
| B2: 24,576 tile draws | **57.2** (data-driven: 88.9) | 14,756 | 11,517 |
| B3: sieve to 4000 + 20,000-step LCG | **29.1** | 1,152 | 26,081 |

* B1 is the arcade number: the job is 8 sprites, erase and redraw, 100 steps. Native does a step in about one frame
  (generic) or 0.57 frame (specialised). BASIC takes 245 frames per step, Leap-C 93. A bytecode VM, even one
  10 to 20 times faster than Leap V2's, cannot move 8 sprites at 60 Hz; only runtime calls into native routines can.
* **Specialising the blitter paid:** 1.78x faster than the generic one, for 2.2x the code (690 B against 313 B)
  plus 512 B of tables, so a per-game blitter (fixed size, pre-shifted copies) is worth generating.
* Leap-C is native but 40x slower than hand code on B3: a stack-machine code generator on the machine is not the
  target. A JS compiler can allocate registers, inline 16-bit arithmetic and peephole, and the hot paths (blit,
  tiles, scroll, collision, sound tick) are runtime routines, not compiled BASIC.

## Size
Hand kernels are 201 to 882 bytes. Leap V2's bytecode for the same programs is 253 to 285 bytes, but that excludes
the 5.9 KB VM and is for plot-per-pixel BASIC. Leap-C's images are 483 to 4,614 bytes. Native costs roughly 2 to 3
times a bytecode program for game logic, which the absence of the VM and the 100x speed more than repay. The G1
size rule (not worse than about 2x) is met once the VM is counted.

## Layout and interrupt findings (xip/)
* Code runs from every DOCK chunk tried; writes to a mapped DOCK chunk are ignored and the RAM under it is hidden.
* A flipping game cannot use chunks 2-3 (`$4000-$7FFF`, the display files). **Layout B** (recommended): runtime and
  code in DOCK chunks 0,1 and 4,5; chunk 6 a paged asset window (no `DI` needed to page it); chunk 7 RAM. That is
  about 40 KB of DOCK and about 10.7 KB of working RAM beside the two display files.
* The frame-interrupt handler flips `$FF` 64-84 T after the interrupt, about 8,900 T before the first pixel
  line; no tearing in 20 frames; handler cost 137 T.
* TSRun **drops** an interrupt that arrives under `DI` (or in the `EI` shadow). Never hold `DI` across a frame
  boundary; paging needs no `DI`.

## Caveats the design must respect
* The fastest native kernels use `SP` as a data pointer and need `DI`; these figures are an upper bound. A real
  game runs a frame interrupt, so such routines must be short (a DI window of N T loses a frame with probability
  N/58,688 on TSRun), or avoid the SP trick. Re-measure with the interrupt handler running (phase 3).
* No contention is modelled; the real TS2068 may contend on `$4000-$7FFF`. Real-hardware check, items 3-4 of the
  notes' checklist.
* The hand-written code is better than any compiler will produce; expect compiled game logic 3x to 10x slower than
  these kernels, which is why hot paths live in the runtime.

## Consequences for the plan
1. Back end: native Z80, statements as inline code or runtime calls. No bytecode VM.
2. Budget: with layout B the cartridge has about 40 KB across DOCK chunks 0,1,4,5,6. The owner's 32 KB is read as
   **32 KB of game (code + assets) with the linked runtime in the remaining 8 KB**; the linker reports both live.
   A one-screen game (no flipping) may also use chunks 2-3 and has more room.
3. The runtime is a per-game linked library (see `docs/ARCADE_PLAN.md`), which this spike supports: specialised
   blitters beat generic ones.
4. Display modes are chosen as families (section 1 of the hardware notes): flipping, 8x1 colour, or hi-res.
