## M2 object layer: the shared specification (both M2 agents work to THIS; where it is silent, choose the simplest thing that works and report it)

Contract text: docs/ARCADE_STUDIO_COMPLETION_CONTRACT.md section 4 "M2. Object layer" and section 8 decisions 4. Review doc text: "No object layer: positions of coins, enemies, the start, keys and doors cannot be placed on the map. An object layer per map: object kinds defined per project (name, marker colour, optional sprite), placed by click, dragged, listed; the Studio writes them into a generated source file (objects.arc: one TABLE per map, ...) that the game reads with LOADTABLE, the way Leap Runner already does by hand."

DATA (fixed; both agents rely on it):
* A map asset (assets.maps.<name>) may carry `objects: [{kind, x, y, props?}]`. `kind` names a key of `project.objectKinds`; `x`, `y` are whole PIXELS of the map (0..w*8-1, 0..h*8-1; the editor snaps to a chosen grid of 1, 4, 8 or 16 px, default 8); `props` is `{propName: integer}` with integers in -32768..32767, holding exactly the props the kind declares (a missing one reads as 0). Unknown keys of an object are kept and written back unchanged. An asset without `objects` is unchanged in every way (a project that has no objects behaves and serialises exactly as before; the stored form stays format 1).
* `project.objectKinds = {name: {colour, sprite?, props: [propName, ...]}}`. Names and prop names are source-safe identifiers: lower-case letter then lower-case letters / digits (<= 12 chars; compile-time arrays are named from them: `<kind>x`, `<kind>y`, `<kind><prop>`, `n<kind>`, `<kind>ix`, so they must not collide with each other, nor with reserved words / built-ins, nor with a project's own names: validate on the Studio side and let the compiler be the final judge). `colour` is a sprite-editor palette index 0..15 (ink + 8 * bright) for the marker; `sprite` is an optional name of a project sprite shown as the marker. At most 16 kinds, 8 props a kind. The key `objectKinds` is OPTIONAL in the project document and in an assets json (arcade/examples/*.assets.json: `objectKinds` beside `maps`), absent = no kinds.
* The generated source (ONE pure function, the single source of truth, in the new module `src/arcade-objects.js`): `generateObjectsSource(assets-or-project-shaped {maps, objectKinds}) -> {text, ... }` writes, in the language of docs/ARCADE_LANGUAGE.md (read the TABLE / LOADTABLE sections and arcade/examples/runner.arc's hand-written `TABLE lv1 .. lv4`, `DIM ...` data block as the model): a header comment saying it is generated and read-only; for each kind used by any map, `DIM` arrays sized to the largest count over the maps (`<kind>x`, `<kind>y`, one per prop, `<kind>ix` the bucket index below, and a scalar count `n<kind>`); then for each map that has objects, `TABLE <map>_objects ... ENDTABLE` with, for each kind, the arrays' contents with that kind's objects SORTED by x (ties: by y, then insertion order) and the count; and, per kind, the optional bucket index `<kind>ix(b)` = index of the first object whose x + width-of-nothing >= b * BUCKET, b = 0 .. ceil(mapPixelWidth / BUCKET), BUCKET = 128 px by default (a per-project setting `project.objectBucket` may override, 0 = no index) — the spatial index scrolling games need (Leap Runner's `cix`). A kind with no objects in a map writes count 0. Output is deterministic and stable (same input, same text byte for byte).
* How the game gets them: `LOADTABLE <map>_objects` (exactly as Leap Runner does for lv1..lv4). Placement of the DIMs / TABLEs in the program text must be valid wherever the generated text lands in the joined source (check where Runner's data block sits: outside every scene, in the game's own state area) — verify with the compiler, and say in your report what rule a game's own source must follow.
* SINGLE SOURCE OF TRUTH FOR COMPILING: every path that compiles a project or an example must give the same program: the Studio (Run, DCK, diagnostics), the `arcadec` CLI with `--assets`, tests' `compileReal`, `publish-runtime`. The Studio shows the generated text as a file named `objects.arc` in the file list, READ-ONLY (cannot be edited in the code editor, not deletable / renamable by the user), rewritten on every change of an object / kind / map, and `buildSource` includes it so diagnostics map into it. For the non-Studio paths, put the hook where the assets reach the compiler (src/lang/arcade/ profile / compile entry or a tiny wrapper), so a game's .arc + assets.json with objects compiles identically with no extra step. A project/assets that has no objects generates NO file and NO text.
